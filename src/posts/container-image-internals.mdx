## sha256은 왜 두 개였을까

빌드 시간을 줄여 보려고 Jenkins 파이프라인 로그를 읽어 봤습니다.

```
#12 exporting manifest sha256:4e285a83…
    └ 빌드가 만든 이미지
...
git-a1b2c3d: digest: sha256:44107a56…
    └ 레지스트리에 올라간 이미지
```

빌드가 만든 이미지와 레지스트리에 올라간 이미지의 주소가 달랐습니다. 이게 무슨 뜻인지 몰랐어요.

이유는 같은 이미지를 두 번 압축하고 있어서였습니다. 그걸 알고 나서 빌드와 푸시 두 단계를 한 명령으로 합쳤고 컨테이너 단계는 23초에서 7초가 됐어요.

## digest는 어떻게 정해지나

컨테이너 이미지는 파일 하나가 아닙니다. 레이어라고 부르는 tar 파일 몇 개와 그 목록을 적어 둔 JSON 문서 몇 장이 서로를 가리키며 붙어 있어요.

<ImageAnatomyDemo caption="이미지의 구성 요소와 그 바깥에 놓인 태그를 한 번에 펼쳐 봅니다" />

이 조각들에는 파일명 대신 digest가 붙습니다. 파일을 sha256에 넣어 나온 값이고 내용이 1바이트만 달라도 값이 완전히 달라져요. git 커밋 해시와 같은 방식입니다.

<ContentAddressDemo caption="입력을 바꾸는 대로 내용 주소가 얼마나 민감하게 반응하는지 보입니다" />

태그만 예외입니다. 계산해서 나온 값이 아니라 사람이 붙이는 이름표라서 다른 이미지로 옮겨 붙일 수 있어요. 그래서 `latest`는 어제와 오늘 다른 이미지를 가리킬 수 있습니다.

레이어 목록을 적어 둔 JSON 문서가 manifest입니다. 여기 적히는 레이어의 digest는 **압축을 끝낸 파일**의 값이에요. 그래서 안에 든 파일이 같아도 압축을 다시 하면 레이어의 digest가 바뀝니다. manifest는 그 digest를 적어 둔 문서라서 manifest의 digest도 함께 바뀝니다.

그러면 두 로그 사이에서 압축이 한 번 더 된 자리만 찾으면 됩니다.

## `--load` 경로를 따라가 보니

누가 압축하는지 찾으려면 어디서 빌드했고 어디로 내보냈는지를 보면 됩니다. 제 파이프라인에서 빌드는 데몬과 떨어진 별도 컨테이너의 BuildKit이 했고 보관과 push는 데몬이 했습니다. 그래서 `--load`로 결과물을 데몬에 내보내는 배달 단계가 필요했고 그 흔적이 로그에 남아 있었어요.

```
#12 exporting to docker image format
    └ OCI → docker 포맷 변환
#12 sending tarball  3.6s
    └ 빌더 → 데몬 배달
#13 importing to docker  1.7s
    └ 데몬이 수납
(그 뒤 docker push ~4s, docker rmi)
```

이미지가 두 번 압축되고 있었습니다. 먼저 BuildKit이 레이어를 압축하고 그 값들로 manifest `4e285a83`을 썼습니다. 그런데 `--load`가 그 압축을 풀어 데몬에 넘겼고 `docker push`가 올리면서 데몬의 gzip으로 다시 압축했어요. gzip은 만든 쪽의 구현과 설정에 따라 나오는 바이트가 달라집니다. 레이어의 값이 바뀌었으니 데몬은 manifest를 새로 썼고 레지스트리에는 `44107a56`이 남았습니다. 압축본을 그대로 보관하는 containerd 저장소를 쓰면 다를 수 있는데 저희 데몬은 클래식 저장소였어요.

<DigestCascadeDemo caption="내보내는 경로를 바꿔 digest가 갈라지는 지점을 찾습니다" />

파일 내용은 그대로라 컨테이너를 띄우면 같은 앱이 돕니다. 달라진 건 압축한 결과의 digest뿐이었어요.

<GzipByteDiffDemo caption="압축 설정이 gzip 스트림을 바이트 단위로 어떻게 바꾸는지 펼쳐 놓았습니다" />

`--push`는 이 중간 경로를 없앱니다. BuildKit이 압축한 그대로 레지스트리에 직접 올려요. 빌드하고 나서 `docker push`를 따로 부르던 두 단계가 한 명령이 됩니다. 배달 왕복 ~5초가 사라지고 다시 압축할 쪽도 없어져요. 대신 데몬에 로컬 이미지가 생기지 않으니 끝의 `docker rmi`도 같이 없애야 합니다.

## 증명서가 따라 붙습니다

속도만 보고 전환하면 놓치는 게 하나 더 있어요.

ARM 맥에서도 인텔 서버에서도 `docker pull nginx`가 되는 이유가 있습니다. 그 태그는 이미지 하나가 아니라 목차를 가리켜요. 목차에는 "amd64용은 이 manifest, arm64용은 저 manifest"가 적혀 있고 pull하는 쪽이 자기 것을 고릅니다. 이 목차가 image index예요.

BuildKit은 이 목차에 이미지가 아닌 것도 끼워 넣습니다. 이미지가 어떻게 빌드됐는지 담은 증명서(provenance)예요. 목차는 항목마다 플랫폼을 적어야 하는데 증명서에는 적을 플랫폼이 없어서 `unknown/unknown`이라는 가짜 플랫폼으로 넣습니다.

`--load`를 쓰는 동안은 이걸 볼 일이 없었습니다. 데몬의 클래식 저장소는 태그 하나에 이미지 하나만 담는 모델이라 목차를 못 받고 증명서도 붙을 수 없었으니까요. `--push`로 바꾸는 순간 그 제약이 사라지면서 태그가 manifest 대신 목차를 가리키게 됩니다. 아무 설정도 안 바꿨는데 결과물의 모양이 달라집니다.

<IndexShapeDemo caption="증명서를 동봉하면 태그가 가리키는 대상이 바뀌고 거기에 걸리는 도구들이 있습니다" />

이건 전환 PR을 다 만들고 나서야 알아챘습니다. 플래그 하나를 바꿔도 전후 동작 차이를 목록으로 만들어 하나씩 지워봤는데 끝까지 지워지지 않은 항목이 이 증명서였어요. 제 파이프라인에는 서명 검증 정책처럼 증명서를 읽는 쪽이 없어서 `--provenance=false`로 기존 형태를 고정했습니다. 빌드와 배포가 성공해도 결과물 모양은 이렇게 달라질 수 있는데 로그에는 그게 안 나옵니다.

## 전환하면서 걸린 것들

전환하면 압축하는 쪽이 달라지니 같은 코드를 빌드해도 레이어와 manifest의 digest가 새 값이 됩니다. digest를 보고 "전에 봤던 이미지인지" 구분하는 시스템이 있다면 전환하는 그 시점에 모든 이미지가 처음 보는 것으로 보여요. 저희 배포 스크립트는 digest를 안 보고 태그만 보기 때문에 아무 일도 없었습니다.

반드시 손봐야 하는 건 하나였습니다. 이미지가 더는 로컬에 남지 않으니 빌드 끝의 `docker rmi`는 지울 게 없어 `No such image`로 실패합니다. 로컬 이미지를 쓰던 단계(`docker run` 확인, 태그 추가)도 같이 깨져요. rmi는 지우고 태그가 더 필요하면 빌드할 때 `-t`를 여러 번 주면 됩니다. `-t`는 만들 이미지에 붙일 태그를 정하는 옵션이고 개수 제한이 없어요. 전에는 로컬 이미지에 `docker tag`로 태그를 덧붙였는데 이제 로컬 이미지가 없으니 빌드할 때 한꺼번에 지정합니다.

나머지 셋은 해당되는 것만 손보면 됩니다. digest를 읽어 저장하거나 비교하는 코드가 있으면 `--metadata-file`로 새 digest를 받아 넘겨줍니다. 증명서는 읽는 시스템이 있거나 도입할 계획이면 기본값대로 켜 두고 저희처럼 아직 없으면 `--provenance=false`로 꺼서 지금과 같은 모양으로 둘 수 있어요. 단일 플랫폼 빌드 기준이고 multi-arch라면 목차는 어차피 남습니다. "이미지 푸시" 같은 별도 단계가 사라지니 그 로그 문구를 찾아 울리던 알림이나 게이트가 있으면 갱신합니다.

## digest 두 개가 하나로

<DigestMatchDemo caption="처음 발견한 두 digest가 전환 뒤 하나로 모입니다" />

로그에서 배달 두 줄(`sending tarball`, `importing to docker`)이 사라졌고 데몬이 다시 압축하는 일도 없어졌습니다.

컨테이너 단계는 23초에서 7초로 줄었습니다. 캐시 상태가 다른 빌드끼리 비교한 값이라 정확하지는 않습니다. 그래도 tar 배달 왕복 5.3초와 데몬의 재압축, 그리고 `docker rmi`가 없어진 것은 확실해요. 이 PR은 머지됐고 운영에도 넣어 문제없이 배포되고 있습니다.
